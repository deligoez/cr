# cr v0.2.2 — The sandbox runs the tests the developer runs

> The release notes for the `v0.2.2` tag.

v0.2.2 implements `spec/0.2.0.md` unchanged. It is a safety release: upgrade, then run `cr init`.

## Why this release exists

A field trial on a real Laravel pull request ran `cr test` and `cr probe run` against the developer's
application database instead of the test database. The repository kept its test database in a gitignored
`.env.testing`; the shipped `laravel-pest` profile copied `.env` into the sandbox but not `.env.testing`, and
Laravel, finding no `.env.testing`, took the database `.env` names. A probe's first baseline also runs the
whole suite, so a filtered probe ran every test there. The repository's tests rolled back their writes, so no
data changed; a repository whose tests rebuild the database would not have been so lucky. The measured
record is in `spec/field-feedback.md` (item 2.1).

**If you are on v0.2.1 or earlier:** upgrade and run `cr init`; the next `cr test` or `cr probe run`
rebuilds any existing sandbox that lacks `.env.testing`. Until you can upgrade, add `.env.testing` to
`sandbox.copy` in `~/.cr/profiles/laravel-pest.json` **and** run `cr sandbox destroy <pr>` for every
existing sandbox: v0.2.1 does not rebuild a sandbox when the copy list changes.

## Changes

- **`laravel-pest` copies `.env.testing`.** Its `sandbox.copy` is `[".env", ".env.testing", "vendor"]`. A
  repository without `.env.testing` is unaffected: an absent entry is reported and skipped.
- **`cr init` updates profiles you never edited.** `cr init` writes profiles into `~/.cr/profiles/` once and
  never overwrote them, so the fix above would not have reached anyone who ran `cr init` before. It now
  rewrites a profile file whose bytes equal the version a previous release shipped (v0.1.0, v0.2.0 or
  v0.2.1), lists it under a new `updated` key, and leaves an edited file alone, naming it under `honesty`.
- **A stale shipped profile is named when it loads.** `cr brief`, `cr review`, `cr status`, `cr post`,
  `cr record`, `cr rules`, `cr sandbox create`, `cr test` and `cr probe run` add a `honesty` line when the
  profile they load is an unedited older shipped version, saying what changed and that `cr init` updates it.
  An edited profile gets no line.
- **An experiment header before every run.** `cr test` and `cr probe run` print, on standard error before
  the runner starts, the runner command, the sandbox path, the clone's gitignored `.env*` files and which of
  those the sandbox also holds, a `not copied` line for each one the sandbox does not hold (naming `sandbox.copy`
  as the fix, or saying the sandbox could not receive a file the list names), the reason when the sandbox was
  just recreated, and — for a probe whose whole-suite baseline has not run at this head — that the whole suite
  runs first. The header survives `--quiet`; the JSON document on standard output keeps its keys, with the
  new sentences under `honesty`. `cr sandbox create` reports the same missing files under `honesty`.
- **A sandbox that is not the clone's is rebuilt.** Before `cr test` and `cr probe run`, an entry of
  `sandbox.copy` that the clone holds and the sandbox lacks, that the sandbox holds and the clone no longer
  does, or a copied file whose bytes differ from the clone's, makes the sandbox stale: it is recreated, and the
  header's `recreated` line and `honesty` say why. A sandbox created before the profile copied `.env.testing`
  — the upgrade path above — is therefore rebuilt on its next run. Directory entries such as `vendor` are
  checked for presence only. Files are compared in memory; their content is never printed or stored.
- **A baseline serves only the sandbox it measured.** Every run record carries the sandbox generation it ran
  in, and a probe uses a baseline only from the current generation, so a suite that passed against a sandbox
  later found stale is not reused. A sandbox created by an earlier cr has no generation and is recreated once
  after the upgrade.
- **Uncopied env files reach JSON.** The sentences naming gitignored env files the sandbox did not receive are
  also under `honesty` in `cr test` and `cr probe run` JSON output.
- **The intent pass waits for the claims.** `cr review <pr> --axis intent` refuses with exit code 4 until
  `cr claims record` has run for the round, because its prompts must carry the claims (§4.6.5); before, it
  emitted prompts saying the round had no claims. An empty claims file counts as recorded, and so do claims
  carried into a moved head's round; a round whose intent axis is unavailable is unaffected (field-feedback
  2.2). For a round briefed from `--intent-file`, the refusal's message names that file in the command
  it gives, since `cr claims record` re-reads the issue; the JSON `hint` field stays generic.
- **New state fields.** `sandbox-baseline.json` gains `generation`, `setup_changed` and `setup_removed`;
  `runs.ndjson` records gain `sandbox`; `meta.json` gains `intent_file`.

## Known limitations

- cr reports a difference between the clone's and the sandbox's env files; it does not refuse to run. A
  refusal needs the profile to say which env files matter, which is spec work planned for v0.3.0.
- When the sandbox's env files do match the clone's, a test suite that rebuilds its database touches
  whatever database those files name — exactly as the developer's own test run would. cr's guarantee is that
  the sandbox reproduces the clone's copied files at the moment of the run, with the exceptions below, and not
  more.
- The header's `in sandbox` line considers only the env files the clone holds: a `.env*` file the sandbox holds
  and the clone does not — one `sandbox.setup` created, or a setup-rewritten file the clone has since lost — is
  on no header line, although the runner may read it.
- A file inside a copied directory is not compared: directory entries are checked for presence only.
- A filtered probe still runs the whole suite once per head as its baseline (§5.2.2); the header now says so
  before it starts. A baseline scoped to the probe's filter is planned for v0.3.0.
- A copied file that `sandbox.setup` itself rewrites (for example `.env` after `artisan key:generate`) is
  excluded from the content comparison, or every run would rebuild the sandbox; an edit to that file in the
  clone is therefore not detected, nor is its removal from the clone. Its presence in the sandbox is still
  checked: a sandbox that lost it is rebuilt.
- A file `sandbox.setup` deletes is asked only to stay deleted, so the sandbox is not rebuilt before every run.
  A sandbox that holds it again is rebuilt once, and the setup deletes it again. The `not copied` line names the
  file for as long as the sandbox runs without it.
- A sandbox built by an earlier cr whose setup created or deleted a file `sandbox.copy` names is rebuilt once
  after the upgrade, because its old baseline did not record that entry as it does now.
- The limitations listed in the v0.2.1 notes still apply.

## Verification

- **Quality gate on a clean clone of the tag's tree**, under Go 1.26.5 and Go 1.27.1, with the tools installed
  by Go 1.27.1: `go test -race -count=1 ./...`, `golangci-lint run`, `scripts/deadcode.sh`, `gofmt -l`, and the
  test suite repeated twice more. All green, `deadcode ./...` unchanged at 11 lines.
- **Four QA passes against a Laravel-shaped fixture** (a clone with a gitignored `.env`, `.env.testing`,
  `.env.local` and a tracked `.env.example`, a `pest` stub reporting which env file it read, and stubs for
  `composer`, `artisan key:generate` and a setup step that deletes a copied file), each in its own `CR_HOME`,
  with `~/.cr` hashed before and after and a `gh` shim that refuses every write:
  - the copy list, the sandbox's env files, the experiment header, the JSON keys, `--quiet`, the honesty
    sentences, the recreation reasons, the sandbox generation and the baselines a probe reuses;
  - the upgrade from a v0.2.1 sandbox, an edited profile left alone, and `cr init`'s `updated` list;
  - the intent-pass refusal, its message for a round briefed from `--intent-file`, and the unaffected cases;
  - every recreation condition in both directions, including the ones that must *not* recreate: an entry
    neither side holds, a setup-created file, a setup-deleted file, and a `touch` that changes no bytes.
- **Three defects found and fixed during those passes**, each with a regression test that drives the command:
  a sandbox missing a copied file was not recreated; a recreation was not named in the header; a setup that
  deletes a copied file rebuilt the sandbox before every run.
- No test, sandbox or probe was run against the repository of the field trial; the fixture is local.

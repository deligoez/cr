# cr v0.4.1 — Three things a run could not do, measured

> The release notes for the `v0.4.1` tag.

v0.4.0 shipped §5.7, the experiment a role can ask for. Measurement 4 then ran it twice — 76 role
sessions against a real pull request, and 22 against cr's own packages with a `go test` sandbox —
and the channel worked: 17 proposals accepted, 9 run, **7 records moved `argued` → `probed`**, all
seven verified by hand afterwards.

The same measurement found three things wrong, and v0.4.1 is those three and nothing else. Two are
`spec/0.4.1.md`, which changes two clauses of v0.4.0's text and leaves the rest alone.

## Install

```bash
brew install deligoez/tap/cr
go install github.com/deligoez/cr/cmd/cr@v0.4.1
```

## A gap probe can now run on Go

Of ten experiments the measurement tried to run, three produced nothing. Two of those were both of
the round's gap probes, and both failed for one reason.

§5.4.2 placed a gap probe's test at one path per profile, `tests.probe_path_template`, and ran the
probe over that file. A Go test is compiled into the package it tests, and the package differs per
probe — so there is no value of a fixed template that works, and cr placed a `package probe` test at
`internal/cli/cr_probe_p2_test.go`. The run was then `go test ./internal/cli/cr_probe_p2_test.go`,
which compiles a lone file as the synthetic package `command-line-arguments`:

```
internal/cli/cr_probe_p2_test.go:30:19: undefined: Target
FAIL    command-line-arguments [build failed]
Tests: 0 ran, 0 failed
```

The result cr recorded was `no-tests-selected`, which is what §5.4.2's rung 3 says for a test that
"failed to load" — honest, and indistinguishable from a filter that matched nothing.

**§5.4.2 now lets the template's directory be `<target-dir>`**, resolved to the directory of the
path in `--target`, and **the probe's own run is scoped to that directory rather than to the placed
file**. A runner that builds a package out of the paths it is handed cannot build one out of a test
file alone; a runner that discovers tests under a path is unharmed by being given the directory.

The same test, the same target, under the new placement:

```
--- FAIL: TestATieOnThePreImageStartDoesNotDependOnHunkOrder/the_insertion_written_first
Tests: 1 ran, 1 failed
```

`result: failed`, over a baseline of 1453 passing — a verdict, where before there was none.

`<target-dir>` is opt-in and may only be the template's first segment; anywhere else aborts with
exit code 2. Every profile cr ships keeps a fixed path and is unchanged. §5.1.6's leftover scan
follows the placeholder: such a template's glob opens `**/`, which `filepath.Glob` reads as a single
segment, so cr walks it instead — an artefact planted two directories down now recreates the sandbox
as §5.1.6 requires.

## The two fields a proposal had that nothing explained

The third lost run was the role's, and it was a prompt defect. §5.7's proposal contract glossed
`kind`, `target`, `hypothesis`, `settles`, `input` and `finding`, then stopped: `filter` and `paths`
were named and never explained. A role filled `paths` with the source file its hypothesis was about,
cr passed it through `tests.paths_arg`, and `go test ./internal/probe/resolve.go` exited on eight
undefined symbols.

Every prompt now says it:

> `filter` and `paths` scope the run, never the code the experiment is about. `filter` is the name
> of a test for the runner to select, not a runner argument string; `paths` are test targets the
> runner understands, the package or directory whose tests are to run, never the file the patch
> changes. Leave both out to run the whole suite, which is the safe answer when you are unsure.

## §8.1.3's reserved sequence is now told to the role

A second fence of the same shape, and it cost a whole unit's work. §8.1.3 reserves `<!-- cr:` for
the record marker and cr's own regions, and §8.1.2 composes a comment's body out of `summary` and
`evidence` — so a record carrying the sequence in either is refused where it enters, and nothing
later can repair it. Nothing told the role the sequence existed.

A role reviewing cr's own draft machinery quoted it in order to name it. `cr record` refused the
record; `cr proposals record` then refused the proposal that named it, for naming no record of the
round. Both refusals are correct and the reservation stands, because it is what keeps a record's
prose from splitting its own draft block. What changed is that the round's contract file now names
the sequence, beside §8.1.5's rule about a question's `?`, and says what to do instead: name it in
words rather than quoting it.

## §3.4.7 names the credential kind

A debt owed since v0.3.2, which shipped the fence and wrote it down only in a release notes file.
`spec/0.4.1.md` §3.4.7 makes a credential-shaped file a third listed kind beside `binary` and
`generated`, with the match rule written out — `.env` and every `.env.*`, `.netrc`, `.pgpass`,
`.htpasswd`, `credentials`, `secrets`, the `id_*` key pairs, and the `.pem`, `.key`, `.p12`, `.pfx`,
`.keystore`, `.jks` suffixes — applied before `ignore.globs`, and no configuration key turns it off.

The behaviour is unchanged. What changes is that the next spec reader learns it from the contract
rather than from a release page.

## Upgrading

Nothing to do. No state format changed, no command gained or lost a flag, and the default placement
of a gap probe's test file is exactly what it was. A profile that wants a Go gap probe to work sets
its `tests.probe_path_template` to something like `<target-dir>/cr_probe_<probe-id>_test.go`.

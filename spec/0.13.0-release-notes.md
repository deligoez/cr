# cr v0.13.0 — House style from the team's own reviews

> The release notes for the `v0.13.0` tag.

Seven of the eight comments cr missed against a careful human reviewer in measurement 3 were house
style, and `cr rules suggest` could harvest only from rounds cr itself had posted, so a team's first
review had no corpus to draw on. v0.13.0 lets the agent draw rules from the repository's own review
history and store them. The contract is `spec/0.13.0.md`: §2.6's new `source` field, §2.6.3.3
reworded, §2.6.3.5 to §2.6.3.9, and two §11 rows.

## Install

```bash
brew install deligoez/tap/cr
go install github.com/deligoez/cr/cmd/cr@v0.13.0
```

## `cr rules suggest --from-history` reports the team's review comments

```bash
cr rules suggest --repo acme/shop --from-history --since 2025-01-01 --until 2026-08-01 --limit 1000 --json
```

cr reads the repository's pull request review comments through gh, newest first, and keeps those
whose `created_at` lies in the window, `--since` inclusive and `--until` exclusive. It stops at
`--limit` opening comments (default 1000) and reports the window it read and whether the limit cut
it. GitHub's own `since` filters on `updated_at`, so cr filters on creation time itself.

A bot's comment (GitHub's `Bot` type, the rule ingestion already uses), a reply, and a comment by the
pull request's own author are excluded and counted by reason; each reply is reported under the comment
it answers. Every included comment carries its pull request, URL, author, time, path, line, side,
body, replies and length in characters, and each month of the window its median length. cr does not
decide which comments an agent drafted: agent-drafted comments arrive under a person's account, and
the month medians are what let the agent choose a window that ends before they began.

The comments are grouped by path shape (`app/Models/*.php`), by backticked code span and by
normalised body, and a group is reported when it spans `rules.harvest_min` distinct pull requests.
Counting pull requests rather than comments is deliberate: one migration can repeat one span dozens of
times on a single pull request. The report lists the ids of the resolved rules and writes nothing.

## `cr rules add` stores a rule the agent wrote

```bash
cr rules add --repo acme/shop negative-test-name.json
```

The file is validated as a §2.6 rule with the loader's own parse, its `detect` pattern compiled,
and written byte for byte to `~/.cr/repos/<owner>/<repo>/rules/<id>.json` under a lock. A malformed
file exits 1 naming the field — it is input, not the corpus file §2.6 item 5 codes 3 — and its id
must be its file stem. An id the per-repository layer already holds exits 4 unless `--replace` is
given. A rule carrying `source`, the URLs of the comments it was drawn from, must be a question: with
`kind: finding` it exits 1, so a rule drawn from history reaches the finding register only by a human
editing the stored file after the team adopts it.

## Measured

Read-only on `tarfin-labs/backend`, 2025-01-01 to 2025-03-01 at `--limit 200`: 318 comments read in
2m16s, 200 included across 19 pull requests, 118 replies excluded and 112 of them attached under an
included comment, no bot and no pull-request author among the opening comments, the limit cutting the
window at 2025-01-30, and month medians of 89 and 30 characters. Whether a corpus seeded this way
recovers what measurement 3 missed is not yet measured; `ROADMAP.md` names the run.

## Upgrading

Nothing to do. A rule file written before v0.13 carries no `source` and reads as it did.

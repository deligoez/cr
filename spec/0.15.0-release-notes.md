# cr v0.15.0 — A result that established nothing erases nothing

> The release notes for the `v0.15.0` tag.

The live tester ran cr 0.14.0 on `tarfin-labs/backend#6328` again and found two places where cr let
a run that established nothing, or a sandbox built for another profile, stand in for the real
thing, and a sandbox that outlived its merged pull request. v0.15.0 settles §5.7.4, §5.1.6 and
§10.4.10; the contract is `spec/0.15.0.md`.

## Install

```bash
brew install deligoez/tap/cr
go install github.com/deligoez/cr/cmd/cr@v0.15.0
```

## Only a decisive result moves a finding's probe (§5.7.4)

On #6328, `f4201` was probed on `p3`, a `no-test-failed` over a passing baseline `r6`. Proposal
`x4202`, naming it, ran with a filter that selected no test and came back `inconclusive` twice
(`p4`, `p5`), and each run moved `f4201` onto the new probe: it ended on `p5`, graded `argued`,
with its evidence region gone from the draft.

When a proposal names a record and its probe's result is `inconclusive`, `error` or `timeout`, the
record now keeps its `probe` and grade. The proposal still becomes `run` on the new probe, and may
run again as v0.14.0 allowed. `cr probe run --proposal` reports it: `regraded` carries
`"kept": true` and `holds`, the probe the record still names, and `honesty` carries the sentence

```
record f4201 keeps probe p3 and grade probed, per §5.7.4: probe p5 came back inconclusive, which establishes nothing, so it moves no record's probe
```

Any other result re-grades the record as before.

## A sandbox is rebuilt when the round's profile changes (§5.1.6)

On #6328 a sandbox built under a custom profile, `laravel-pest-paths`, which copied
`storage/*.key`, survived switching the repository's configuration to `laravel-pest` and a second
`cr brief`. `cr test` kept running with keys the new profile does not copy, and no missing-key
notice appeared until `cr sandbox destroy`.

The post-setup baseline now records the id of the profile the sandbox was built under. A baseline
that records no profile, or a profile other than the round's, is not Clean: the next `cr test` or
`cr probe run` recreates the sandbox and names the cause in its `recreated` line, as in
`it was built under profile laravel-pest-paths, and the round's is laravel-pest`. The rebuilt
sandbox holds what the round's profile copies, so a `not copied` line appears for each gitignored
file it lacks.

## A closed pull request's sandbox is named (§3.7.1, §10.4.10)

On #6328 a sandbox of 439 MB, holding copies of `.env` and Passport's keys, outlived its merged
pull request, and nothing cr printed said it was there.

- `cr brief` records the state of a pull request that is not open in `meta.json`, as `pr_state`
  (`merged` or `closed`) and `pr_state_at`, the time GitHub reports. Both keys are absent while
  the pull request is open.
- When the round's last brief found the pull request not open and its sandbox exists, `cr next`
  ends with a `sandbox` step, taken by the agent, naming the state and
  `cr sandbox destroy <pr> --repo <owner>/<repo>`.
- `cr status` reports the sandbox while it exists: a `sandbox` field with its `path`, `bytes` (the
  regular files under it; a symbolic link is not followed), `since` (when the post-setup baseline
  was recorded, or the directory's modification time when no baseline names one) and
  `age_seconds`, and one `sandbox:` line of text. The field is absent when there is no sandbox.

The skill now ends the loop by destroying the sandbox, and says that the sandbox separates files,
not the test database: a copied `.env.testing` points the suite at the same database, so the suite
is not run by hand while cr runs it.

## Upgrading

Every existing sandbox is rebuilt once. No baseline written before v0.15.0 records a profile, so
the first `cr test` or `cr probe run` on each pull request recreates its sandbox, runs the
profile's `sandbox.setup` again, and reports
`its post-setup baseline names no profile, so what it was built with is unknown`. The probe that
follows performs §5.2.2's baseline again, because the new sandbox is a new generation.

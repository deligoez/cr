# cr v0.2.1 — Known defects and two limitations of v0.2.0, repaired

> The release notes for the `v0.2.1` tag.

v0.2.1 implements `spec/0.2.0.md` unchanged: a patch release carries no normative change. It repairs
every defect v0.2.0 shipped knowing about and closes two of its documented limitations. Nothing in it can
change what a posted review asserts; the repairs are in counts, hints, locks and process handling.

## Install

```bash
brew install deligoez/tap/cr
go install github.com/deligoez/cr/cmd/cr@v0.2.1
```

## Repairs

- **Set-asides on a retracted note.** `cr status` counts in `set_aside` only claims whose set-aside note
  still stands; a claim whose note was retracted is listed under `unstanding_notes`, and in a terminal
  its gap line reads `(set-aside note <id> retracted)`. Before, the count said 1 while the same output's
  §10.2 reason said the claim was not set aside.
- **Intake counts.** A finding given to both `cr record` and `cr merge`, in either order and any number of
  times, is counted once in `rounds/<n>/summary.json` (`raised`, `waived.dropped`,
  `already_posted.dropped`). The per-record keys that make this possible live in a new round file,
  `rounds/<n>/intake.json`; `summary.json` keeps counts only, per §6.4.4.
- **Marker moved out of its unit.** The refusal keeps the problem text `cr record` gives and now ends
  with the marker's own way forward: keep the comment within its unit or delete the block.
- **Inconclusive probes say why.** A mutation or gap probe answered `inconclusive` carries a `reason`
  naming its rung, and the exit code when the run reported zero failures but exited non-zero.
- **`--repo` and the clone's remote.** When the pull request's commit is missing and `--repo` names a
  repository no GitHub remote of the clone points at, the hint names both repositories and the
  `git fetch https://github.com/<owner>/<repo> pull/<n>/head` step. A fork remote that holds the
  commits is not refused.
- **`cr context` and the key pattern.** `cr context` refuses an issue key `intent.key_pattern` does not
  match, with exit code 1, as `cr note` does. A note stored by v0.1 under such a key is still removable
  with `cr note --remove <id>`.
- **One fetch hint.** A head or merge base missing from the clone gives the same `git fetch` hint and
  exit code 3 on every command that reads it — `cr brief`, `cr status`, `cr review` and `cr post`
  included — through one check; a git failure of another kind keeps its own hint.
- **Rule fixes follow detection.** The fix `cr record` attaches to a record naming a rule is built only
  from hits in files that formed a unit, the scope §2.6.1.1 gives detection.

## Limitations closed

- **The probe lock spans state roots.** Besides the lock under `CR_HOME`, a probe or test run takes a
  second lock keyed by the clone's path and the profile id in the temporary directory, so two state roots
  no longer run suites on one clone at the same time. Its scope is the temporary directory: per user on
  macOS, where `$TMPDIR` is per user. On Linux, where it is `/tmp`, runs by one user serialise; a run by
  a different user on the same clone is expected to fail opening the lock file rather than wait, which
  has not been measured.
- **No runner outlives a killed `cr`.** The test runner is held until `cr` has recorded its process
  group. If `cr` is killed with SIGKILL in between, the runner never starts, so there is no unrecorded
  runner for the next command to miss. The runner's argv, environment and working directory are
  unchanged.

## Known limitations kept

- A runner interrupted by SIGINT or SIGTERM is killed, nothing is recorded, and the command exits 4.
- The refusal of a new record id outside its prompt's block applies only once `cr review` has emitted
  that round's prompts.
- `cr status` on a moved head omits the reinvention and symbol halves and the file counts, and says so.
- A malformed `--json` value such as `--json=maybe` is refused with exit 2, in prose on a terminal.
- A notes store written by v0.1 that mixes spellings of one issue key on a case-insensitive disk is still
  listed mixed under the key `cr context` accepts.
- Anchors are not migrated across a head change; that is v0.3.

## Upgrade notes

- A round opened on v0.2.0 keeps its intake counts when continued on v0.2.1: an intake entry with no keys
  in `intake.json` is counted as v0.2.0 counted it.

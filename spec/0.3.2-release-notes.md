# cr v0.3.2 — What a run must not hand on

> The release notes for the `v0.3.2` tag.

v0.3.2 implements `spec/0.3.0.md` unchanged: a patch release carries no normative change. It closes the two
defects the roadmap listed before any feature, both measured end to end before they were fixed: a secret
that reached every prompt, and a process of the test runner that outlived the run without a word.

## Install

```bash
brew install deligoez/tap/cr
go install github.com/deligoez/cr/cmd/cr@v0.3.2
```

## The fixes

**A file whose name says it carries a secret no longer forms a unit, so its content reaches no prompt.**

Measured at v0.3.1, by driving `cr brief` and `cr review` over a pull request whose head adds a tracked
`.env`: `ignore.globs` defaults to no glob, the file is not binary and the repository does not declare it
generated, so `internal/unit/files.go`'s sort clustered it and `internal/review/text.go` wrote its added
lines into every role's prompt inside a fenced `diff` block, verbatim —

~~~
## Unit u1 (§3.4)

.env, RIGHT side, formed by adjacency, 1 changed line(s), hunk ranges 1-1.

```diff
@@ -0,0 +1 @@
+AWS_SECRET_ACCESS_KEY=…
```
~~~

Such a file is now a third kind beside §3.4.7's `binary` and `generated`: `credential`. It is **listed by
path and not clustered**, so the brief and `cr status` both name it — `.env (credential)` in a terminal,
`{"path": ".env", "kind": "credential"}` in JSON — and no prompt carries its text. Nothing is hidden from
the reviewer; what is withheld is the content from a model.

The fence is read **before** `ignore.globs`, which is the part that matters and the reason it is not a
setting. §2.7's layers replace a list value outright rather than merging it, so shipping the fence as a
default glob would have it disappear the moment a repository set `ignore.globs` for its own reasons, and
an excluded file is counted, not named. Tested first, the file is always named.

Matched, case-insensitively, on the base name: `.env` and any name beginning `.env.` (a `.env.example`
included, because telling a template from a real file by its name is a guess this fence must not make);
`.netrc`, `.pgpass`, `.htpasswd`; `credentials`, `secrets`; `id_rsa`, `id_dsa`, `id_ecdsa`, `id_ed25519`
and their `.pub` forms; and the extensions `.pem`, `.key`, `.p12`, `.pfx`, `.keystore`, `.jks`.

**A process of the test runner that outlives the run is disclosed.**

v0.3.1 bounded the wait after §5.2.3's kill, so a process that left the runner's group no longer blocks
`cr test` and `cr probe run` for ever. It was still neither killed nor reported: cr never learns such a
process's pid and cannot signal it, so the honest remedy is to say so, and saying nothing let a run report
a sandbox and a test database that something else was still using.

The instrument is the runner lock, which every process the runner started inherits as an open descriptor.
Once cr closes its own hold, the lock is held by exactly the processes of that run that are still alive.
When it is still held two seconds later, `cr test` and `cr probe run` disclose it, whatever the run's
result was and without changing that result. The grace is what separates a survivor from a child still
shutting down; measured, it costs a run that left nothing behind nothing, because the first probe of a
free lock succeeds.

The notice states only what was observed from outside. Which process holds the lock, and whether it left
the group or merely outlived its parent, is not something cr can establish, so the sentence does not say
it. This is `spec/field-feedback.md` M-1.6's remaining half.

**The `laravel-pest` profile ships four house-style rules.**

§2.6's rule corpus is where a team's conventions live, and cr shipped none at all, so a team's first review
— where style matters most — had nothing. Measurement 3 is the evidence: seven of the eight comments cr
missed against a careful human reviewer were shaping comments, which are neither in the issue nor in the
diff. The four rules are the misses that recur: a negative test named `it_does_not_...`, a local read once,
a variable named for where a value came from rather than what it holds, and fixture setup repeated across
tests. Only the first carries a detector; the other three are injected as text under §2.6.1.4.

They ride in the profile's `rules` array, which §2.6 item 1 already names as the third and lowest layer, so
nothing new was added to the contract. **Every one keeps the default `question` register**, and that is the
decision rather than an oversight: a team that never adopted these rules did not declare them, and an
assertion of house style cr invented is exactly the wrong comment this project spends its trust on. A team
that does adopt one overrides its id at the global or per-repository layer, where `kind` and `severity` are
theirs to set.

## Also

- The stale-profile notice no longer claims that `cr init` will leave the sandbox short of a file it copies
  unless `sandbox.copy` is one of the fields that actually moved.
- `internal/profile/builtin/shipped/` gains the `laravel-pest` bytes of v0.2.2, v0.2.3, v0.3.0 and v0.3.1,
  which is what keeps a user holding them inside `cr init`'s update.
- `README.md` and `skills/cr/SKILL.md` say that a credential-shaped file is listed and not clustered.
- `internal/cli/credentialfence_test.go` drives `cr brief`, `cr claims record` and `cr review` over such a
  pull request and asserts the secret is in no prompt. Run against the unfixed sort through `go test
  -overlay`, it fails on the leak itself.

- `internal/cli/runnersurvivor_test.go` drives `cr test` and `cr probe run` over a runner that leaves a
  process behind, and asserts the notice reaches the honesty channel of both and no other run. With the
  detection removed through `go test -overlay`, both go red.

## Not in this release

- The normative clause for the credential kind. §3.4.7 names two kinds without closing the set, so listing
  a third contradicts no MUST, but it is not written down either; the clause is owed to the next spec
  revision.
- Killing a survivor. cr cannot signal a process whose pid it never learned, and §5.6.3 already says the
  lock covers cr's own runs only. Disclosure is the whole of the remedy here.

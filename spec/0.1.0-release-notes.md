# cr v0.1.0 — Review a pull request without spending trust

> The release notes for the `v0.1.0` tag, the first release.

`cr` is a code review lifecycle manager for AI coding agents. It reviews a pull request someone else
wrote: it reads the intent from the tracker, proves that every changed unit was examined, grades every
finding by the evidence behind it, and hands the human a draft to edit before anything is posted.

`cr` never calls a language model. It fetches, executes, validates and records; the agent driving it
forms the judgements. `spec/0.1.0.md` is the normative contract this release implements, and
`VISION.md` explains the bet behind it.

## Install

```bash
brew install deligoez/tap/cr
go install github.com/deligoez/cr/cmd/cr@v0.1.0
```

`cr` needs `git`, an authenticated `gh`, and a tracker command (`intent.cmd`, default
`jira issue view {key} --plain`) unless the issue text is passed with `--intent-file`. State lives
under `~/.cr/` (`CR_HOME` overrides it). The Claude Code skill that teaches an agent the loop ships at
`skills/cr/SKILL.md`.

## What v0.1 does

- **Intent coverage, both ways.** Claims are extracted from the issue and every changed unit is mapped
  to them. An unmapped hunk becomes a question; a claim nothing implements is a gap `cr status`
  reports, unless a note sets it aside.
- **Evidence sets the register.** `cr` grades every record itself: `probed` (an experiment supports
  it), `cited` (it points at code outside its own unit), or `argued`. An `argued` record is posted as a
  question, and no flag, setting or environment variable changes that.
- **Findings carry experiments.** `cr test` runs the profile's suite in a throwaway worktree; a
  mutation probe breaks a line to show a test gap and a gap probe runs a new test against the head.
  Every probe reverts, including when the run fails, times out or panics.
- **Coverage is proven.** Every unit times every active role is a filled cell, and an axis or lens
  that is disabled or unavailable is reported with its reason in `cr brief`, `cr review`, `cr status`
  and the posted review body. A changed file the selected profile's symbol index does not cover is
  named there, rather than prompted as if it declared nothing.
- **Parallel roles do not collide.** Every prompt `cr review` emits states the record schema's value
  domains and names a block of record ids no other prompt of the round is given.
- **The human is the author of record.** `cr draft` renders an editable draft; deleting a block waives
  it for the pull request, `disposition="wrong"` waives it repository-wide and counts against its class.
  Nothing reaches GitHub without `cr post --confirm`, all comments land in one review, and a round posts
  at most one. Comment bodies follow `render.lang` (default `tr`); the review body is English.
- **An unknown outcome is settled, not retried blind.** A 5xx, a timeout or an unparseable answer from
  the review call exits 4 and marks the round; `cr post --confirm`, `cr draft` and a moved-head
  `cr brief` refuse until `cr post --reconcile` adopts the review GitHub created or clears the mark.
- **Conventions are data.** Project rules live in a layered corpus with their rationale, can carry a
  mechanical `detect` block and a ready suggestion, and `cr rules suggest` proposes rules from comment
  bodies posted repeatedly.
- **`cr` never writes inside the repository under review.** The worktree, index and branch are
  read-only to it; every `git` call goes through a pinned runner that inherits an allowlisted
  environment.

v0.1 ends at posting. When the pull request's head moves, open records go stale and `cr brief` opens a
new round; following the conversation after posting (`recheck`, `verify`, `resolve`) is v0.2.

## Where this release reads the spec a particular way

- **§9.3.3.** While a round carries an unsettled post (`post_unresolved`), `cr brief` refuses a moved
  head with exit 4 instead of opening the new round §9.3.3 describes, because opening it would strand a
  review GitHub may already hold. Run `cr post <pr> --reconcile` first.
- **§5.4.4.** The at-least-high severity floor binds a gap probe that supports its finding. A failed
  probe whose result does not support the finding sets no severity bound: the record's grade stays
  `argued` and it is posted as a question.
- **Review thread ids.** Pairing an ingested thread with the review that created it assumes GitHub's
  REST `node_id` for a review equals its GraphQL id, as GitHub documents. It has not been measured
  against a live API; if the two differ, `cr` stores no thread id rather than a wrong one.

## Known limitations

- The "next free id" hint in `cr merge`'s and `cr record`'s id refusals names the round-wide next id,
  not the next id in the refused prompt's own block; following it during a parallel fan-out can
  collide with another prompt's block.
- `summary.json`'s `raised` count covers what `cr merge` saw; records handed straight to `cr record`
  are not added to it.
- `cr config --resolved` shows the per-repository layer only when given `--repo`, and does not say
  it skipped that layer otherwise.
- The disclosure of a lens that did not run is worded for the operator (it names the profile glob to
  add) and reaches the posted review body as written.

## How it was built

The spec went through a counted review loop before decomposition, and the implementation was built as
314 tasks with `tp`, one commit and one closure each, every closure behind the quality gate
(`go test -race ./...`, `golangci-lint run`, `./scripts/deadcode.sh`). The implementation audit ran 14
rounds against the spec, recorded in `spec/.tp-review/0.1.0/`. Round 13 came back clean; round 14, a
fresh look at every file changed since round 1, raised seven findings of warning or info severity, and
a QA run against a real pull request raised five more, one of which mattered most: a review body
claiming no lens was left unexamined while one had seen none of the changed files. All of them are repaired in
this release. The tag was cut on those repairs rather than on a further pair of clean audit rounds.
`govulncheck ./...` reports no vulnerability the code calls.

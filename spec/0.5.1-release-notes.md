# cr v0.5.1 — A posted concern survives the push

> The release notes for the `v0.5.1` tag.

v0.5.0 closed the loop: after the author replies or pushes, `cr recheck` reads back what changed,
`cr verify` records the judgement, and `cr resolve` and `cr withdraw` close the thread. The same day
it shipped, a design question about `cr withdraw` led to a check of where a posted record actually
lives. It turned up the one case v0.5 was written for, broken: **after the author pushes, none of the
four commands could see a posted record.**

v0.5.1 is that fix and one smaller one found beside it. `spec/0.5.1.md` changes two clauses of
v0.5.0's text and leaves the rest alone.

## Install

```bash
brew install deligoez/tap/cr
go install github.com/deligoez/cr/cmd/cr@v0.5.1
```

## After a push, the posted concerns were gone

A push moves the head, and `cr brief` opens a new round for it. §9.3.4 moves the old round's unsent
records to `stale` and leaves posted ones alone, as v0.5 intends: a posted concern has to survive the
push so it can be verified against it. But the posted record stays on its own round's line, and
nothing carries it into the new round. `cr recheck`, `cr verify`, `cr resolve` and `cr withdraw` all
read only the current round's records, so after the push:

```
cr recheck 12        ->  "concerns": []
cr verify 12 f3 …    ->  record f3 is not a record of round 2
cr withdraw 12 f3    ->  record f3 is not a record of round 2
```

Nothing in the test suite could see this. Every v0.5 test put the posted record into the round the
command read, so each one tested the loop inside a single round, and a single round is exactly the
case that never needs the loop.

**The four commands now find a record by its id in whichever round holds it**, and a verdict or a
withdrawal changes the record's state in the line that holds it. The line keeps its round and its
head, so the record still says which run wrote it and against which commit its anchor was taken.
`cr recheck` lists every posted record of the pull request; its migrations are still the current
round's own. A record id is stable for the life of a pull request (§6.1), so an id names one record
across every round.

The obvious fix is to copy each posted record into the new round. It was rejected because it breaks
three other things. `cr post` would read the copies as comments the new round had already sent and
refuse its review. The round's triage report would count them as raised a second time. And unit ids
are per round, so a copy's `u1` would silently mean a different piece of code.

`TestAPostedConcernOutlivesThePushThatMovesTheHead` makes a real second commit, runs a real
`cr brief` over it, and then drives all four commands. Run against v0.5.0's command files, it fails at
`cr recheck`'s concern list and at `cr withdraw`.

## `cr rules suggest` stopped counting a comment once it was settled

§2.6.3.1 harvests "comments posted from recorded rounds". v0.5.0 read that as records in the state
`posted`. That was the same set through v0.4, when `posted` was final. In v0.5, `cr verify` and
`cr withdraw` move a record out of `posted`, and the harvest then dropped a comment the author really
did receive. The more concerns a reviewer settled, the less of their review history the harvest could
see.

The harvest now takes every record whose comment reached GitHub: `posted`, and the three states v0.5
moves it to. The set is derived from §9.1's transition table rather than written out, so a fourth exit
added later is harvested without anyone having to remember this line.

## Upgrading

Nothing to do. No state format changed and no command gained or lost a flag. A posted record that
v0.5.0 appeared to lose after a push was never deleted: it is still in its round, and v0.5.1's
`cr recheck` lists it again.

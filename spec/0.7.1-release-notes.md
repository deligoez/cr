# cr v0.7.1 — One git process where there were nine thousand

> The release notes for the `v0.7.1` tag.

v0.7.1 is the first thing cr's first review of a real pull request taught it. The round ran on
`tarfin-labs/backend#6292`, a Laravel repository with about nine thousand source files, and the
commands were slow: `cr status` took 57 to 82 seconds and `cr record` more than five minutes. The
contract is still `spec/0.7.0.md`; nothing cr reports changed.

## Install

```bash
brew install deligoez/tap/cr
go install github.com/deligoez/cr/cmd/cr@v0.7.1
```

## Where the time went

A `git` on `PATH` that logged every call cr made counted **8,913 git processes for one
`cr status`, and 8,895 of them were `git cat-file blob`**. That is one process per source file of
the head, started by §4.3.1's symbol index, which reads every file the profile owns so it can offer
pre-existing symbols as reinvention candidates. Half of the run was spent in the kernel.

The index now reads the whole head through one `git cat-file --batch`. On the same pull request and
the same state, `cr status` takes **3.8 seconds and starts 29 git processes**, and its output is
byte-for-byte the output v0.7.0 printed. `cr brief`, `cr review` and `cr record` build the same index
and speed up with it; `cr brief` now takes 5.8 seconds there.

The new read goes through the same pinned git runner as every other one, and the guard that holds
cr's git subcommands to a read-only list reads it too.

# cr v0.6.0 — Beyond one stack and one tracker

> The release notes for the `v0.6.0` tag.

Through v0.5, cr ran fully only on a Laravel repository with Pest tests whose issues lived in Jira.
Anywhere else, the test axis had no runner, every probe came back `inconclusive`, and the first
review needed a tracker command written by hand. v0.6 opens both doors: a `go` profile that ships,
and GitHub Issues as a tracker that needs nothing configured beyond the `gh` cr already requires.

It also makes a withdrawal count, fixes the two confirmed writes v0.5 could never perform, and
lets `cr status` see the concerns a push leaves behind.

## Install

```bash
brew install deligoez/tap/cr
go install github.com/deligoez/cr/cmd/cr@v0.6.0
```

## `cr resolve --confirm` and `cr withdraw --confirm` now reach GitHub

**If you use v0.5.0 or v0.5.1, this is the reason to upgrade.** Both confirmed commands were
refused by GitHub every time. The resolve mutation passed its thread id as one field named
`variables` holding a JSON object. `gh api graphql` turns every field except `query` into a GraphQL
variable with that field's name, so GitHub received a variable called `variables`, and `$thread`
arrived empty:

```
gh: Variable $thread of type ID! was provided invalid value
```

The thread is now passed as `-f thread=<id>`. We checked this against GitHub without changing
anything, by sending a thread id that does not exist. The old form answers with the error above.
The new one answers `Could not resolve to a node with the global id of '…'`, which means the
variable arrived. Nothing had caught this. The package test asserted the broken argument list as
correct, and its stub answered "resolved" to any call. The new test's stub resolves a thread only
when it receives the argument GitHub reads, and fails with GitHub's own error otherwise.

## A Go profile

`cr init` now writes `go.json`, which a repository with a `go.mod` selects on its own. It runs
`go test -v -count=1`, runs `./...` when a round names no path, and places a gap probe's test
beside its target, because a Go test compiles into the package it tests.

`go test` prints no summary line with a count on it, so the profile uses a new counting mode,
`tests.count_mode: occurrences`. In this mode cr counts the matches of each pattern instead of
adding up a number captured from each match. The patterns are anchored at the start of the line, so
they count top-level tests and not the indented subtests below them. Skipped tests are not counted,
for the same reason `laravel-pest` leaves them out: a run of nothing but skips must not look like a
run in which nothing failed.

**No test lines counts as zero only when the run exited 0.** A tree that does not compile also
prints no test lines, and exits 1 with `FAIL <pkg> [build failed]`. Read as zero tests, that would
have reported "your filter matched nothing" about code that never built. It now reads as
undetermined instead. The profile's tests run against real go1.27.1 output captured from a module in
five states: all passing, some failing, a filter matching nothing, skips only, and a build failure.

§2.4.5 no longer says how many profiles ship. It lists them and requires that every one except
`generic` sets a runner, both count patterns, a filter flag and a probe path. A fourth profile is
then an ordinary commit, and the requirement applies to it automatically.

## GitHub Issues as a tracker

```json
{"intent.tracker": "github"}
```

With this in a repository's configuration, cr never starts `intent.cmd`. The issue is the one the
pull request closes, as GitHub links it: a closing keyword in the body, or the Development panel. A
`#12` mentioned in plain prose is not a link and is not read. Measured on real pull requests,
GitHub's own parser makes exactly this distinction, and a regex over the body cannot. `--issue`
takes `12`, `#12`, `owner/repo#12`, the issue's URL, or the key itself. The text is the issue's
title and body.

The key is written `owner.repo#12`, not `#12`. An issue number is unique within one repository and
nowhere else, and cr keeps its context notes per key. With a bare `#12`, every repository's twelfth
issue would share one store, and a note from one project would reach another's review.

cr reads the issue through the same `gh` door it reads the pull request with, not through a
configured command. That door runs with an allowlisted environment, so `GH_REPO`, `GH_HOST` and
`GH_TOKEN` cannot redirect the read to someone else's repository with the same name. Two cases are
refused rather than guessed:
- **A pull request that closes several issues** is refused until `--issue` names one.
- **A number GitHub answers as a pull request** is refused. GitHub numbers issues and pull requests
  from one sequence, and `gh issue view 1` on a repository with no issues returned pull request #1
  without complaint. Read as the intent, a pull request's own description would review the change
  against itself.

## A withdrawal is evidence now

```bash
cr withdraw 12 f3 wrong --confirm
cr withdraw 12 f4 not-here --confirm
```

A concern the author has read and the reviewer has then taken back is the strongest signal about a
class that cr can collect, and v0.5 threw it away. `cr withdraw` now needs to be told which kind of
retraction it is, because cr cannot tell a false concern from a true one that was not worth the
comment:
- **`wrong`** writes a repository-wide waiver and counts against the class in `cr stats`.
- **`not-here`** writes a waiver for this pull request only and counts toward volume, never against
  the class.

The outcome replaces the `kept` the posting wrote, so one raised record still has exactly one
outcome, and the statistics still add up to the number of records raised.

The waiver needs no git checkout. `cr record` now stores the waiver key's hash with the anchor, at
the moment it reads the lines anyway. A withdrawal can come after the author pushed, even
force-pushed, and the commit the record was made against may then be gone from the clone. The hash
is computed from exactly the same input as before, so every waiver and posted-index entry written by
an earlier release still matches.

`cr stats` gains two columns, `withdrawn_not_here` and `withdrawn_wrong`.

## `cr status` sees posted concerns from every round

A posted record stays in the round that posted it. So from the second round on, `cr status` counted
none while `cr recheck` listed several. It now reports `posted_concerns`: every record still posted,
with the round that posted it. They still do not block completeness.

## Upgrading

- **`cr withdraw` now requires `wrong` or `not-here`** after the record id. Without one it exits
  with code 2.
- **A repository with a `go.mod` now selects the `go` profile on its own.** Before, no profile
  matched and the test axis was off. Run `cr init` to write `go.json`. To keep the old behaviour,
  name another profile in the repository's configuration.
- **Records written from now on carry `anchor.context_hash`.** Earlier records don't, and still
  work: their key is read from the tree, exactly as before.
- **Nothing else in the stored state changed format**, and no other command gained or lost a flag.

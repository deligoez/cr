# cr v0.5.0 — The loop closes

> The release notes for the `v0.5.0` tag.

Every version of cr through v0.4 ended at the same place. It oriented on a pull
request, reviewed it across four axes, proved what it could with experiments,
drafted, took a human's triage, and sent one review — and then had nothing to
say. The author replied; cr could not read it. The author pushed; cr could not
tell whether the concern still stood. A reviewer who wanted to close a thread
closed it by hand, and a concern that turned out to be wrong stayed on the pull
request because nothing retracted it.

v0.5 is the other half, and one change carries it: **`posted` stops being a
terminal state.**

## Install

```bash
brew install deligoez/tap/cr
go install github.com/deligoez/cr/cmd/cr@v0.5.0
```

## Four exits instead of none

§9.1's table gave `posted` no way out, because the loop ended there. It now has
four:

| From | To | Meaning |
|---|---|---|
| `posted` | `answered` | The author's reply settled a posted question |
| `posted` | `addressed` | The concern is gone at the current head |
| `posted` | `withdrawn` | The reviewer retracted it |
| `posted` | `posted` | It still stands, carried into the round |

The fourth is not a transition, and it is the one that changes how a round
reads: a concern nobody has settled is **open**, not finished. §7.3's statistics
and §10.2's completeness now count an `answered` record as settled and a
`posted` one as still open — the difference a convergence rule is made of, and
one that did not exist while both sat under the same word.

## `cr recheck` reads back, and judges nothing

```bash
cr brief 1        # the author pushed; the new round opens, posted records survive it
cr recheck 1
```

```json
{
  "round": 2,
  "concerns": [
    {"id": "f2", "thread": "PRRT_kwDO…", "kind": "finding", "outdated": true,
     "resolved": false, "line": 0, "original_line": 6,
     "replies": [{"author": "the-author", "body": "Fixed in 49d8bca."}]}
  ],
  "migrated": [
    {"record": "f5", "from": "order.go:12", "to": "order.go:31",
     "placed": true, "key": "content", "candidates": 1}
  ]
}
```

`line: 0` beside `original_line: 6` is what an outdated thread looks like: the
head no longer carries the code, and GitHub keeps the original so the thread
still names a place. cr reads `line`/`original_line` and **never REST's
`position`** — measured on a real pull request, three comments originally at
lines 9, 44 and 44 all report `position: 1` once the head moves, so a reader
trusting it would place three concerns on one line and believe it had
succeeded. §9.5.2 writes that down so nobody simplifies the read later.

## A migration that cannot be made unique is not a migration

GitHub re-anchors the comments it holds. What cr owns — records not yet posted —
it migrates itself, and §9.4 is deliberately reluctant about it.

The match is by hash, because a record stores its anchored lines' `content_hash`
and not the lines. When one run of lines in the head matches, that is the
migration. When several do, the recorded context window narrows them. When it
still cannot make the answer unique, **cr declines**: the record keeps the
anchor it had and is reported `placed: false` with how many candidates the last
key left — `0` meaning the code is gone, `2` meaning it is now in two places.

Declining is cheap; the record becomes a question or is withdrawn, and §7.2
still requires a human's edit before anything posts. Placing a comment on a line
that merely resembles the old one is a wrong assertion carrying a confident
location, which is the most expensive thing cr can produce.

Two constraints on that migration are measured rather than assumed. It reads
**only the current head's tree and what cr stored**, never the superseded
commit — after a force-push that commit is absent from a fresh clone and cannot
be fetched by SHA, so a migration needing it would work only where the old
objects happened to survive. And a candidate with fewer lines available on one
side than the record recorded there does **not** survive the window: the
permissive alternative was tried first, and it matched a candidate sitting at
line 1 against a record that had recorded a line above it, placing the anchor on
the wrong one of two copies.

## You judge; cr records

```bash
cr verify 1 f2 addressed --evidence "49d8bca adds the guard; the probe no longer reproduces"
cr verify 1 f7 standing  --evidence "the reply asks for time and changes nothing yet"
```

Three verbs, and the third earns its place: `standing` moves nothing and is
recorded anyway, because a concern somebody read and left open is a different
fact from one nobody read. `--evidence` is required, stored verbatim, and never
parsed — §6.2.1's rule about a record's own evidence, applied to a judgement.

**cr does not reach this verdict itself, and §9.5.6 says why.** Every signal it
can read — an outdated thread, a probe that stopped reproducing, an author
writing "fixed" — is exactly as consistent with a concern that was addressed as
with one whose code was moved, renamed or deleted. P5 gives cr no standing to
tell those apart, and the cost of guessing lands on a human's name. The
tempting design is the one where `cr recheck` concludes, and it is tempting
precisely because the evidence is usually unambiguous.

`answered` is a question's word: a finding given it is refused, because §9.1.3
counts an answered record as settled and the word would have every convergence
figure count a finding nobody dealt with as dealt with.

## Closing a thread, behind the same gate

```bash
cr resolve 1 f2 --confirm
cr withdraw 1 f9 --confirm
```

`cr resolve` refuses a record nobody settled — resolving a thread over an open
concern hides it, which is worse than leaving it open, because nobody looks
again. `cr withdraw` retracts a concern that should not have been raised.

**A withdrawal posts no prose, and that is a constraint rather than a gap.**
§8.1.2 gives cr one channel for a body a human wrote — the draft — and a flag
here carrying text to GitHub would be a second. A reviewer who wants to tell the
author why writes that reply themselves, which is what §7.2.3 already says about
every comment cr does not compose.

Both writes go through §8.5's gate and through `internal/gh`'s single door.
There are now three gates rather than one, and each still takes a flag it just
read as its only input, which is what §8.5.3 actually requires.

## Also in this release

- §5.3.4's and §5.4.3's zero-count rungs carry a `reason` naming the exit code
  when it is not 0. A run that did not compile and a filter that matched nothing
  both report `no-tests-selected`, and reading that word and stopping there is
  what made measurement 4's first write-up blame the wrong clause for two of its
  three lost runs. §5.5's table also gains the `reason` row the implementation
  had been writing without one.

## Upgrading

Nothing to do. No state file changed shape; `verdicts.ndjson` and
`migrations.ndjson` are new rows in §2.3's table and are created empty with the
directory. A round recorded by v0.4 reads unchanged — its posted records simply
become open, which is what lets you verify them.

# cr v0.2.0 — The reviewer loop, repaired against a real pull request

> The release notes for the `v0.2.0` tag.

`cr` is a code review lifecycle manager for AI coding agents. It reviews a pull request someone else
wrote: it reads the intent from the tracker, proves that every changed unit was examined, grades every
finding by the evidence behind it, and hands the human a draft to edit before anything is posted.

v0.2.0 is the v0.1 loop after a 478-case QA pass against a real scratch pull request
(`deligoez/cr-qa`). The pass raised 57 distinct defects across 14 slices, and every one is repaired
here. Where a repair needed the contract to change, the change is in `spec/0.2.0.md`, which is the
normative contract this release implements.

## Install

```bash
brew install deligoez/tap/cr
go install github.com/deligoez/cr/cmd/cr@v0.2.0
```

`cr` needs `git`, an authenticated `gh`, and a tracker command (`intent.cmd`, default
`jira issue view {key} --plain`) unless the issue text is passed with `--intent-file`. State lives
under `~/.cr/` (`CR_HOME` overrides it). The Claude Code skill ships at `skills/cr/SKILL.md`.

## What changed in the contract

Each item below is a normative change from `spec/0.1.0.md` to `spec/0.2.0.md`.

- **A zero failed count counts only on a clean exit (§5.3.4, §5.4.3).** A mutation probe answers
  `no-test-failed`, and a gap probe `passed`, only when the probe run's `exit_code` is 0. A runner that
  printed a zero failed count and then exited non-zero is `inconclusive`: it establishes nothing, and a
  record resting on it stays `argued`.
- **A gap probe whose runner exited on a signal is `error` (§5.4.3),** as a runner that never started
  is. A crashed process no longer falls through to `failed`, which would have carried a severity of at
  least `high`.
- **The draft marker carries `side` (§7.1.1, §7.2).** The marker has nine fields, with `side` between
  `path` and `start_line`:
  `<!-- cr:record id="f1" kind="question" path="internal/api/handler.go" side="RIGHT" start_line="42" line="44" severity="high" grade="argued" disposition="" -->`.
  An edited side is re-validated with the lines, and a marker without `side` is malformed.
- **Waivers and the posted index are keyed by the anchor's context window (§7.4.1, §9.3.6).** The key's
  hash is the §1.4-normalised hash of the context lines before the anchor, the anchored lines and the
  context lines after, joined by LF. A waiver now stops suppressing once the code around the anchor
  changes, not only the anchored lines. The anchor's own `content_hash` and every citation hash still
  cover the anchored or cited lines alone.
- **The review is pinned to the round's head (§8.3.4).** The review-creation request names the round's
  head as `commit_id`, and `posted.json` records it, so GitHub places every comment on the diff cr
  validated rather than on whatever head the pull request has at the time of the call.
  `cr post --reconcile` adopts a review only when its commit is that `commit_id` and no earlier round's
  posted-index entry holds its id (§8.4.4).
- **`head` and `round` are computed (§3.3, §6.1).** §3.3's table now marks a claim's `head`, and §6.1's
  a record's `round` and `head`, as computed, matching what `cr` does: it writes them per §2.3.3 and
  refuses a line that supplies one.
- **Rule detection runs over the units' lines (§2.6.1).** A `detect` pattern is evaluated over the added
  and modified `RIGHT`-side lines of the units of §3.4 only. A file `ignore.globs` excludes, and a
  binary or generated file `cr` lists without clustering, produce no hit and no `rule-stats.ndjson`
  line.
- **An unsettled post blocks the commands that could post twice (§8.4.4, §9.3.3).** While `meta.json`
  carries `post_unresolved`, `cr draft`, `cr post --confirm` and a `cr brief` on a moved head refuse
  with exit 4 and name `cr post <pr> --reconcile`. v0.1 already refused the brief; §9.3.3 now says so.
- **A closed or merged pull request is disclosed, never refused (§3.7, §8.5.1).** `cr brief`,
  `cr status` and a `cr post` dry run name the state and the time GitHub reports, first in `honesty`,
  and `cr post --confirm` prints it on standard error before the request. Whether to send stays the
  reviewer's decision at `--confirm`.
- **Completeness waits for the intent pass (§10.2.5).** While the intent axis is active, a round is not
  complete until `cr claims record` and `cr map record` have run for it. A round with neither recorded
  used to read complete, because the claim condition holds over zero claims.

The re-review half of the loop — `recheck`, `verify`, `resolve`, `accept`, and anchor migration across a
head change — moves from v0.2 to v0.3 (§1.3.6). v0.2 ends at posting.

## QA repairs

Grouped by where a user meets them. The commit subjects in `git log v0.1.0..v0.2.0` carry the detail.

- **Recording.** A LEFT anchor on a line the diff did not remove, and a RIGHT anchor on a unit that only
  removes lines, are refused; a deletion-only unit is numbered in the merge base and measured at its
  insertion point. `cr merge` refuses every anchor `cr record` refuses. A new record id outside its
  prompt's id block is refused, with a hint naming a free id inside that block, and id blocks stay fixed
  across a re-brief that changes the active roles. `cr review --axis ""` is refused with exit 2.
  `cr cells record` refuses a repeated seat, an unknown key, a test-axis cell without `test_paths`, an
  `na` cell beside a record, a cell citing a note that no longer stands, and off-axis cells before the
  mapping; `cr record` refuses a record at a seat holding an `na` cell. `summary.json`'s `raised` count
  includes records handed straight to `cr record`.
- **Brief and status.** `cr brief` reports every lens that did not run, as `cr review` and `cr status`
  do, reports the records a new round moved to `stale`, and stops offering a reply the context store
  already holds. A new round keeps the earlier rounds' units and mapping in state instead of
  overwriting them. `cr status` names the seats missing a cell, counts an empty claims recording as the
  round's claims, reports `post_unresolved`, and on a moved head names both heads without reading the
  recorded head the clone may lack. `cr brief` and `cr status` ask for a head the clone never fetched
  and exit 3 with a hint naming `git fetch`.
- **Review prompts.** Quoted thread comments are fenced; file-level threads and a unit file's outdated
  human threads are listed; a rule hit's fix suggestion appears in the prompt, and rules the profile's
  scope leaves out are listed.
- **Probes and the sandbox.** A patch line `cr` does not execute (a rename, copy or mode header) is
  refused, and so is a patch naming a file the sandbox lacks, both with exit 1. A probe recorded as
  `error` carries its `reason`. An unusable baseline, an unstarted runner and a voided probe are
  explained. The test runner is stopped when `cr` is interrupted or killed, and a sandbox whose setup
  failed is removed.
- **Draft and post.** The draft prints the comment cap and keeps the round's forcing counts and new
  classes after records are discarded; a changed marker id names the edited marker, and the moved-block
  refusal names the escape. The
  posted suggestion is range-checked and its indentation warning is computed on what is sent. The
  review body words a lens that did not run for the author. `cr post --reconcile --confirm` is refused
  with exit 2, and a multi-line comment is named by its whole range.
- **Notes and intent.** `cr note` refuses invalid UTF-8, an off-pattern issue key and an unknown answered
  record; note claims are judged against their note, and a retracted set-aside counts as unsettled.
- **Configuration.** A config layer `cr` cannot use exits 3 naming the file, key and layer; a protected
  `CR_` variable, a protected config key such as `grading.argued` in either config file, and a
  protected field such as `forcing` in any profile file are refused with exit 3 on every command,
  `cr init` included; a configured profile that is not a file stem is refused. `cr config` consults the detected repository's layer.

All four known limitations v0.1.0 listed are repaired: the next-free-id hint, the `raised` count,
`cr config --resolved` without `--repo`, and the operator-worded lens disclosure in the review body.

## Upgrade notes

- **Old waivers and posted-index entries stop matching.** Entries written by v0.1 carry the hash of
  the anchored lines alone, so under the new key they match nothing — except for an anchor whose
  context lines are empty or blank, where §1.4's normalisation leaves the two hashes equal. A finding
  once waived or once posted will be raised again by the next round. v0.1 waivers still decode, and
  `cr waivers list` and `cr waivers remove` still show and remove them. Posted-index lines have no
  remove command; they stay in state and match nothing.
- **A draft rendered by v0.1 is refused.** Its markers lack `side`, so `cr draft` and `cr post` refuse
  it with exit 1 naming the line and the record, for example
  `draft line 11, record f1, is a malformed record marker: " side=" does not follow, and §7.1.1 fixes the nine fields and their order`.
  `cr draft` reads the existing draft back before it renders a new one, so it refuses too. Add each
  record's anchor side (`side="RIGHT"` or `side="LEFT"`) between `path` and `start_line` in every
  marker, then run `cr draft` to regenerate the file.
- **The review request carries `commit_id`.** The body `cr post --confirm` sends is `commit_id`, `event`,
  `body` and `comments`, and `posted.json` stores the same `commit_id`. For a `posted.json` written by
  v0.1, which has none, `cr post --reconcile` holds a review's commit against the round's head.

## Known limitations

- The probe lock is per `CR_HOME`. Two `cr` processes with different state roots do not serialise their
  runs against the same repository.
- If `cr` is killed with SIGKILL after the test runner starts and before `cr` records the runner's
  process group, the next `cr test` or `cr probe run` has no recorded group to stop.
- A runner interrupted by SIGINT or SIGTERM is killed, nothing is recorded, and the command exits 4.
- The refusal of a new record id outside its prompt's block applies only once `cr review` has emitted
  that round's prompts; before that, no block is measured.
- `cr status` on a moved head omits the reinvention and symbol halves and the file counts, and says so.
- `cr review` and `cr post` on a head the clone never fetched fail at git rather than with the
  `git fetch` hint `cr brief` and `cr status` give.
- A malformed `--json` value such as `--json=maybe` is refused with exit 2, in prose when standard
  output is a terminal, because the flag that would ask for JSON is the one that failed to parse.
- The fix suggestion `cr record` generates for a record naming a rule re-evaluates the rule over the
  whole round diff, not only the files that formed a unit.
- A probe whose runner reports zero failures and exits non-zero is `inconclusive` with an empty
  `reason`; the exit code is on the run's line in `runs.ndjson`.
- A marker edit in the draft is held to `cr record`'s unchanged-lines refusal, and `cr post` refuses a
  position outside the diff, but neither refuses an anchor the reviewer moved into a different unit.
- Anchors are not migrated across a head change; that is v0.3.

## How it was built

v0.1.0 was built as 314 `tp` tasks and audited in 14 rounds. v0.2.0's repairs were built after it, one
commit each, behind the same quality gate (`go test -race ./...`, `golangci-lint run`,
`./scripts/deadcode.sh`).

**v0.2.0 was not audited by `tp`.** By the user's decision on 2026-09-14, the implementation audit was
replaced by the 478-case QA pass against `deligoez/cr-qa` and a targeted re-run of the QA cases the
repairs touched. This is an exception for this release, not a change to the audit rule in `CLAUDE.md`.
